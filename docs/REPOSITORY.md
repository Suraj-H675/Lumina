# Repository structure

## Top-level ownership

```text
apps/
  api/                 Python application package and tests
  web/                 Next.js application and tests
packages/
  api-client/          generated OpenAPI schema/types + safe transport
  config-typescript/   shared TypeScript compiler configuration
data/
  audits/              active quality/evidence artifacts
  manifests/           reviewed provenance manifests
  reviews/             review evidence associated with data products
  seed/                curated reviewed scientific/model artifacts
  sky/                 reviewed sky-context metadata
migrations/             immutable applied Alembic history
scripts/
  bootstrap/           local environment/bootstrap helpers
  ci/                  repository/CI validators and evidence tools
  data/                scientific-data validation commands
  openapi/             deterministic API-client generation
infra/                  local infrastructure setup
.github/                CI and contribution templates
docs/                   current documentation
```

## Principles

- A directory should exist because it has an owner and active contents, not because a roadmap once predicted it.
- Do not create empty future-phase folders.
- Avoid two manually maintained canonical copies of the same artifact.
- Generated artifacts must have an explicit generator and freshness check.
- Historical migration files remain where they are and are not reorganised for aesthetics.
- Tests stay close to the owning application (`apps/api/tests`, `apps/web/tests`) unless they validate repository-wide tooling.

## Generated and ignored state

These are intentionally local/generated and must not be committed:

- `.env`;
- virtual environments and package-manager installs;
- `.next` and browser test output;
- Python/type-check/lint caches;
- private upload storage under `var/storage`;
- temporary CI/security artifacts.

`apps/web/next-env.d.ts` is generated by Next.js and intentionally ignored by the web package.

## Documentation

Project documentation is tracked. Historical implementation diaries should be removed or summarized once they stop helping contributors understand the current system.
